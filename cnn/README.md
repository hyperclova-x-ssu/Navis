# Navis CCTV 분석 (CNN)

매장 카메라 영상에서 **손님 수, 자리별 이용 상태, 치울 테이블, 음료를 기다리는 자리**를 계산하는 영상 분석 코드입니다.
휴대폰을 카메라로 쓰고, GPU 서버에서 실시간으로 분석해 Navis의 CCTV 현황 위젯으로 숫자를 보냅니다.

| 항목 | 선택 |
| :--- | :--- |
| 탐지 | YOLO11s (COCO 사전학습) — 사람·컵·의자·테이블 |
| 추적 | ByteTrack + 칼만 필터, "확인된 추적"만 손님으로 셈 |
| 자리 판정 | 테이블 구역 마스크 + 머문 시간 + (선택) 자세 추정으로 앉음/서 있음 구분 |
| 실시간 서버 | Python, FastAPI, WebSocket (휴대폰 카메라 → 서버 → Navis 화면) |
| 최적화 | GPU 없는 매장 PC(CPU 4코어·8GB) 기준 OpenVINO INT8까지 측정 |

목업용 실험입니다. 앱 화면에는 연결하지 않았고, 숫자를 실제로 뽑아 정답과 비교만 합니다.

## 하는 일

Café 영상 17번(카메라 1대) 클립 354~403(연속 50개, 약 5분, 1,718장)을 시간 순서로 이어서 YOLO11s(COCO 사전학습, 새 학습 없음)로
person·cup·chair·dining table을 찾고, 사람은 ByteTrack으로 이어 추적합니다. 구역 규칙으로 아래 숫자만 뽑습니다.

- 손님 수: 프레임별 사람 수(평균·최대), 5분간 서로 다른 추적 번호 수(참고값)
- 줄 길이: 줄·주문 구역 안 사람 수(평균·최대)
- 자리: 테이블 구역 사람 있음/없음, 앉은 자리 수, 머문 시간(초)
- 치울 테이블 후보: 사람 없음 + cup 있음(1분 중 절반 이상 프레임)

## 구역 정하는 법 (`make_zones.py` → `zones/cafe17.json`)

카메라가 고정이라 구역도 고정 다각형입니다.

1. **줄·주문 구역**: 정답에서 Queueing·Ordering 사람 상자의 **아래쪽 중앙점**을 모아, 바깥 5%를 빼고 볼록 껍질을 만든 뒤 80px 키움.
2. **테이블 구역**: Eating/Drinking·Working/Studying 사람 상자의 아래쪽 중앙점을 가까운 것(200px)끼리 묶어 묶음마다 볼록 껍질(80px 키움). 이 카메라에서는 한 묶음(table1, 창가 안쪽 부스 자리) 하나만 나왔습니다. dining table 탐지는 구역 정하는 데 쓰지 않았습니다.
3. 정답 상자는 탐지 상자보다 위쪽·작게 그려져 있어서, 정답의 아래쪽 중앙점이 탐지 상자 중심점과 위치가 비슷합니다. 그래서 탐지 쪽은 **상자 중심점**이 구역 안인지 봅니다(눈으로 확인한 경험 값).
4. 안쪽 부스(앉은 사람)와 앞쪽 줄이 화면에서 겹쳐 보여서, 상자 높이가 400px 이하면 앉은 사람(테이블 구역), 크면 앞에 선 사람(줄·주문 구역 검사)으로 나눕니다.

**주의**: 정답 라벨로 구역을 만든 것은 실험 편의입니다. 실제 매장에서는 사장님이 설정 화면에서 한 번 그립니다.

## 한계

- 구역을 정답 라벨로 만들었습니다. 정답과 구역이 같은 데이터에서 나와서 줄·자리 점수가 실제 매장보다 좋게 나올 수 있습니다.
- 장면은 참가자가 연출한 것이고, 카메라 1대·5분이라 시간대 변화나 다른 시점은 검증하지 못했습니다.
- 줄 길이 오차가 큽니다. 정답 줄 인원은 가려지거나 상자가 다르게 그려진 경우가 많고, 구역이 앞쪽 사람과 겹쳐 놓친 사람이 있습니다. 줄 구역을 더 넓히거나 정답 기준을 맞추는 조정은 하지 않았습니다.
- 정답 상자와 탐지 상자의 위치 정의가 달라 구역 경계는 눈 확인에 의존합니다.
- 테이블이 1개 구역뿐이라 자리별 비교·치울 테이블 후보는 사실상 시험하지 못했습니다.
- 픽업대·주문 기록은 이 데이터에 없어 다루지 않았습니다(주문 대기·누락은 team/CNN.md 4.5절 방식).

## 탐지 화면용 결과 만들기 (T-042, `export_playback.py`)

Café 실험의 미리 계산된 영상(`/cnn/cafe17.mp4`)과 상자·숫자(`/cnn/cafe17-detections.json`)를 만듭니다.

현재 앱 예시는 직접 촬영한 영상과 `zones/store-sample.json`을 사용합니다. `cnn`에서 `.venv/bin/python export_store_sample.py <영상 경로> --ffmpeg <libx264를 지원하는 ffmpeg 경로>`로 `store-sample.mp4`와 `store-sample-detections.json`을 만듭니다.

```sh
cd cnn
.venv/bin/python export_playback.py              # 전체(약 1~2분): 영상 + json 둘 다
.venv/bin/python export_playback.py --video-only # 영상만 다시 인코딩(json은 그대로, 약 12초)
.venv/bin/python export_playback.py --recompute  # 모델 없이 기존 json의 상자로 t·판정만 다시 계산(수 초)
```

T-041과 같은 모델(YOLO11s + ByteTrack, mps)로 17번 클립 354~403(1,718장)을 시간 순서로 처리합니다. 결과는 `frontend/public/cnn/`에 생기며 커밋 대상은 이 두 파일뿐입니다.

**`cafe17.mp4`**: 상자 없는 원본 장면, 960×540, 5fps(r_frame_rate 5/1, 원본 6프레임 간격), 약 344초, H.264 yuv420p, `+faststart`, 소리 없음, crf 30(약 20MB).

**`cafe17-detections.json`** (좌표는 모두 0~1 비율, 소수 셋째 자리):
- `fps`(5, 영상과 같음; `frames[i].t` = i/5 초, 마지막 343.4), `frameCount`(1718), `width`, `height`, `source`
- `tables`: `[{id, name, polygon:[[x,y],...]}]`
- `frames[]`: `t`(초), `persons`: `[x1,y1,x2,y2,trackId,seatedTableId|null]`, `cups`: `[[x1,y1,x2,y2]]`(T-046d부터 cup·wine glass·bowl만. 의자·테이블·병 없음), `counts`: `{inStore, seated, inStoreRaw, seatedRaw, occupiedTables, tablesToClear}`(T-046부터 `inStore`·`seated`는 다듬은 정수, `*Raw`는 다듬기 전, `persons`는 확인된 추적만. 아래 "숫자 안정화")
- `summary`: `avgInStore`, `maxInStore`, `tableOccupiedSeconds`, `tablesToClearEvents[{table, fromT, shownT, toT, hiddenT}]`, `smoothing`

**판정 규칙**
- `inStore` = 그 프레임의 사람 수(T-041 손님 수와 같은 방식).
- 앉음(T-046b) = 사람 상자 **위에서 80% 지점**(엉덩이·발 쪽, 가로는 가운데)이 테이블 구역 안 + 상자 높이 ≤ `maxBoxH`(350px, 서 있는 사람 제외). 상자 중심을 쓰면 비스듬한 카메라에서 서 있는 사람이 테이블 구역에 걸려 오차가 컸습니다.
- 치울 테이블 = 구역 안에 사람은 없고 cup이 있는 상태(cup이 1초 안에 잠깐 안 잡히면 이어진 것으로 봄)가 조건. **표시 시작**: 조건이 연속 3초 이어진 시점. **표시 끝**: 표시 중 조건이 연속 3초 이상 끊겨야 숨김(3초 안에 다시 성립하면 계속 표시, 가까운 구간은 하나로 이어짐). `frames[].counts.tablesToClear`는 `shownT`~`hiddenT` 프레임에만 넣어 표시 구간이 최소 3초다. 이벤트 `fromT`=조건 시작, `shownT`=표시 시작(3초 확인), `toT`=조건이 마지막으로 성립한 시각, `hiddenT`=끊김 3초 확인(숨김) 시각. 영상 끝에서 끊김 확인이 끝나지 않은 이벤트는 마지막 프레임까지 표시하고 `hiddenT`는 확인됐다면의 시각(영상 길이를 넘을 수 있음)으로 적는다. 모델 재실행 없이 `python export_playback.py --recompute`로 다시 만든다.

**테이블 구역 정하는 법(T-046b)**: `python tune_tables.py --write`가 정답(Eating/Drinking·Working/Studying) 사람 상자의 점(상자 위에서 50% 지점, 정답 좌표는 1280×720 기준이라 ×1.5)을 20px 격자로 줄여 가까운 것끼리 묶고(150px 이내, 80칸 이상) 볼록 껍질을 80px 키워 `zones/cafe17_tables.json`에 씁니다(`{id, name, maxBoxH, polygon}`, `footFrac`=0.8). 데이터가 말한 구역은 **1개(t1 창가 테이블 구역)**였고, 2개로 나누면 오차가 더 커졌습니다(36%). 구역·값은 정답 오차가 가장 작은 조합으로 골랐습니다(pad 0~200, 묶음 거리, 점 위치, maxBoxH 격자 탐색). 구역을 바꾸면 `python export_playback.py --recompute`로 모델 없이 다시 계산합니다.

**다시 만드는 법**: 위 명령을 다시 실행하면 두 파일을 덮어씁니다. 사진은 `~/Datasets/cafe-sample/`(저장소 밖)이 필요합니다.

## 숫자 안정화 (T-046, `smooth.py`)

화면 속 사람 수가 사진 한 장(초당 5번)마다 바뀌어 너무 빠르게 출렁였습니다. 근거와 조사는 [team/CNN.md 4.7절](../../team/CNN.md). 모델은 다시 돌리지 않고, 이미 뽑은 프레임별 상자(추적 번호 포함)에 두 단계를 얹었습니다.

1. **확인된 추적만 세기**: ByteTrack 추적 번호가 **연속 N장 이상** 잡힌 장부터 그 사람을 셉니다(추적 번호 없는 상자·N장 미만은 `persons`에서 뺌). N=2.

원본 상자는 `results/cafe17_raw_persons.json`에 보관하며 `python export_playback.py --recompute`가 이것으로 확인·칼만·비교를 모델 없이 다시 계산합니다(`smooth.py`의 `MIN_TRACK_FRAMES`, `KALMAN_Q`, `KALMAN_R`를 바꾸면 반영).

### 정답 정의 (D-376: "앉음" → "점유"로 통일)

- **occupied(새, 주 비교)**: 테이블 구역에 머무는 손님 = 정답 행동이 줄 서기·주문이 **아닌** 사람(식사·작업·셀카·Fighting·무리 밖 모두). 활동 라벨이 아니라 "그 자리에 있는가"로 봅니다. 데이터 전체에 같은 규칙을 자동 적용했습니다.
- **정답 기준점 자동 보정**: 정답 상자는 가려진 다리까지 그린 상자라 탐지 상자보다 깁니다(앉은 사람은 탐지 높이가 정답의 0.65~0.73배). 그래서 정답의 80% 지점은 몸에서 더 아래에 찍혀 t4 손님처럼 구역 밖으로 나갔습니다. 앞쪽 절반에서 정답·탐지 상자를 짝지어(IoU ≥ 0.5, 탐지 기준점이 구역 안, 3,181쌍) "탐지 80% 지점이 정답 상자 위에서 몇 %인가"의 중앙값 = **0.681**을 정답 기준점으로 씁니다(뒤쪽 절반은 0.687로 같음). 정답과 예측이 같은 몸 위치로 구역을 판정합니다.
- **seatedOld(옛, T-046d)**: 식사·작업·셀카 + 80% 지점. 나란히 냅니다.
- 두 정의 모두 무리 밖(outlier) **포함 / 제외**. "머문 인원 오차" = 같은 정의의 테이블별 인원 합, 칼만 후 상대 오차. 손님 수는 판정과 무관(확인된 추적 수, 칼만 후).
- **규칙 때문에 바뀐 칸**(6,872칸 = 1,718장 × 4테이블, outlier 포함 기준): 활동 규칙만 바꾸면 533칸(모두 빔→사용 중), 기준점 보정까지 902칸(빔→사용 중 836, 사용 중→빔 66).
