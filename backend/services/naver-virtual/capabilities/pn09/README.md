# PN-P1 provider contract

The internal provider represents the fictional 안숭잘부 카페 with assumed owner and partner approvals. The Place, booking, order, SmartCall and funding recommendation routes use the private `/partner-assumed/v1` contract. The café uses general-type booking and an eligible linked POS for ordering. NAVER supports this combination; the restaurant-specific booking type currently lacks ordering. [General-type products](https://help.naver.com/service/11712/contents/17285?lang=ko) · [Type and order eligibility](https://help.naver.com/service/30026/contents/20705) NAVER, CLOVA and SENS receive zero traffic from the provider fixtures.

All HTTP routes require the foundation's private workload and account headers. The owning Navis domain revalidates the owner, card, revision and expiry before calling a write. Cancel requires the extra confirmation in the domain. Partner writes take a durable `Idempotency-Key`. The P/O response contains only the projection below. Every `ref` is a private persona selector. The funding list's HTTP `Link` header is private transport metadata. P/O errors use HTTP status and generic Navis envelopes; adapters must never attribute these diagnostics to NAVER.

## Published wires

- **AiCall Custom Condition V2.0**. `deliverAiCallFixture` sends `userId,userKey,userVariables` to an approved private customer callback. Each variable uses string `value` and `typ`, including JSON text for date (`year`, `month`, `day`, `name`) and time (`hour`, `minute`). The configured fixture creates a candidate intake request and accepts the documented `reservationFailed` branch while owner review is pending. The call has no reservation completion effect. [V2 JSON](https://guide.ncloud-docs.com/docs/chatbot-chatbot-2-3), [AiCall reservation scenario](https://guide.ncloud-docs.com/docs/clovaaicall-aicall-1-9)
- **Npay online merchant**. Approval uses `POST /naverpay-partner/naverpay/payments/v2.2/apply/payment`. Cancel uses `POST /naverpay-partner/naverpay/payments/v1/cancel`. Both use HTTP forms and the official merchant headers. Duplicate keys return HTTP 409 with the original response and echo the official idempotency header. The runtime requires a separately staged eligible payment within the documented approval deadline. The pinned café seed stages `PN09BOOKED01` for the Compose test. [Approval](https://docs.pay.naver.com/docs/onetime-payment/payment/apply/), [cancel](https://docs.pay.naver.com/docs/onetime-payment/payment/cancel/), [auth](https://docs.pay.naver.com/docs/common/authentication), [idempotency](https://docs.pay.naver.com/docs/common/idempotency)
- **Npay transaction settlement**. Reads use `GET /naverpaysettle-payment/naverpaysettle/v1/settlements/by-case/{payment-id|pay-hist-id}/{searchkey}`. The first-page pagination counters are numeric per the official field table. The same source's historical example quotes its counters. Confirm the observed upstream representation before live sign-off. Approval delivers the current false/zero settlement placeholders. Deposits and signed reversal amounts come from the independent settlement fixture for `PN09SETTLED01`. [Settlement](https://docs.pay.naver.com/docs/settlement/settlement-api/settle-by-case/)
- **Npay Connect**. The owner terminal path retains its known tender references via POS. [Connect](https://www.navercorp.com/media/pressReleasesDetail?seq=33567)

## Local Compose proof

Run these commands from the repository root using the existing `navis-backend-local-tools:latest` image. The proof project uses an internal Docker network and its own disposable PostgreSQL storage.

```sh
docker compose -p navis-pn-p1-proof -f backend/services/naver-virtual/capabilities/pn09/compose.test.yaml up -d db customer persona
docker compose -p navis-pn-p1-proof -f backend/services/naver-virtual/capabilities/pn09/compose.test.yaml run --rm proof verify
docker compose -p navis-pn-p1-proof -f backend/services/naver-virtual/capabilities/pn09/compose.test.yaml restart persona
docker compose -p navis-pn-p1-proof -f backend/services/naver-virtual/capabilities/pn09/compose.test.yaml run --rm proof restart
docker compose -p navis-pn-p1-proof -f backend/services/naver-virtual/capabilities/pn09/compose.test.yaml run --rm proof reseed
docker compose -p navis-pn-p1-proof -f backend/services/naver-virtual/capabilities/pn09/compose.test.yaml down -v
```

PN01 uses local persona safety bounds of 100 characters for a place name, 300 for
an address, 50 per keyword, and 8–20 digits or hyphens for a phone number. The
five-keyword count is documented by [SmartPlace](https://help.naver.com/service/30026/contents/20366).
