# POS sale and postpaid table handoff

Record a walk-in sale when the owner explicitly completes checkout in POS. The owner enters cash received or records a payment already made on the store terminal. Use the order and receipt reads for the same transaction after reloading.

## Routes

The browser prefix is `/api/v1/stores/{storeId}/pos`. Forward the same suffix to `/internal/v1/pos/stores/{storeId}` using the account-authorized store, actor and owner role. Reuse the POS gateway-owner registrar and its transaction before calling `registerPosRealityRoutes(owner, tokens, { readCatalog })`. Pass the parsed query as the fifth handler argument and support `PATCH` and `DELETE`. Mount either the operating owner routes or the fixture owner routes in a service instance, since some paths overlap. Keep the private customer claim routes on their separate credential.

| Method and suffix | Request and result |
| --- | --- |
| `GET /tables`, `GET /tables/:id` | Table UUID, `layoutTableId`, label, seats, state, revision, active `billId` and `openedAt`. While cleaning, `lastBillId` is the bill that released the table. List status is `empty`, `occupied`, `cleaning` or `archived`. Default excludes archived tables. |
| `POST /tables` | `{ label, seats, layoutTableId? }`. Pass the existing shop layout's table ID, such as `T1`, to register its mapping. An active mapping is unique per store. Registering the same mapping again returns the existing table. Labels are 1–40 characters and unique among active tables regardless of case. Seats are integers from 1 to 30. |
| `PATCH /tables/:id` | `{ expectedRevision, label?, seats?, state?: "empty" }`. Use `state: "empty"` to finish cleaning. |
| `DELETE /tables/:id` | `{ expectedRevision, confirmed: true }`. Archives an empty table. |
| `GET /bills`, `GET /bills/:id` | Bill ID, state (`open`, `paid`, `void`), revision, business date, order type, table UUID, timestamps, quote, `orderIds`, nullable `settlementId` and `paymentId`, and `remaining`. |
| `GET /coupon-sales?businessDate=YYYY-MM-DD` | Owner read. Returns `businessDate`, `asOf`, `hours` (`businessDate`, store-local `hour`, `count`), `visits` (distinct `businessDate`, `hour`, `memberId`), `menuFrequency` (`menuId`, `count`) and `soldToday` (`menuId`, `quantity`). History covers the 28 business dates before `businessDate`. Hour counts use positive net sales. `soldToday` reverses canceled quantities and keeps units from prepared refunds. `view=today` reads only `soldToday` and returns empty history arrays. |
| `POST /bills` | `{ type: "dine_in" \| "takeout", lines: [{ menuId, qty, optionIds? }], discount?, table?: { tableId, expectedRevision }, postpaid?: true }`. A dine-in request with `table` or `postpaid:true` creates the first accepted order and returns `orderId` and `orderIds`. A table reference uses the POS UUID. The receipt always contains a `quote` with `quoteRevision`, `lines`, `gross`, `discount` and `payable`. Other requests use the original walk-in draft flow. |
| `POST /bills/:id/orders` | `{ expectedRevision, lines: [{ menuId, qty, optionIds? }] }`. Appends an accepted order to the current postpaid bill. Returns `quote`, the new `orderId` and all `orderIds` on the bill. |
| `POST /bills/:id/move` | `{ expectedRevision, table: { tableId, expectedRevision } }`. Moves the same bill to a free table and returns its receipt and quote. |
| `POST /bills/:id/merge` | `{ expectedRevision, targetBillId, targetExpectedRevision }`. Moves allocations from the source to the occupied target and voids the source. Returns the target bill receipt and quote. |
| `POST /bills/:id/split` | `{ expectedRevision, table: { tableId, expectedRevision }, lines: [{ orderLineId, qty }] }`. Moves a strict subset of the source quantities to a new bill at a free table and keeps the original orders. Returns the new bill receipt and quote, and the updated `sourceRevision` of the original bill. |
| `POST /receipts/:id/undo` | `{}` with the transfer's `receiptId` and a new idempotency key. Restores affected bills, allocations and sessions while keeping subsequent kitchen progress. Requires the same owner, an open day, unchanged affected bills and tables, and the original six-second `undoUntil`. |
| `POST /settlement-quotes` | `{ billId }`. Read-only reprice for an open bill in the current business day. Returns `{ billId, quoteRevision, lines, gross, discount, payable }`. |
| `POST /bills/:id/payments` | `{ method, amount, quoteRevision, terminal? }`. `method` is `cash`, `card` or `easy_pay`. `amount` is integer won and equals the quote payable. Returns a payment receipt with `billId`, `orderId`, `orderIds`, `paymentId` and `settlementId`. |
| `POST /bills/:id/void` | `{ expectedRevision, confirmed: true }`. Voids an open unpaid bill and releases its active table. |
| `GET /orders`, `GET /orders/:id` | Order ID, number, date, ordered time, revision, `preparation`, nullable `preparingAt` and `completedAt`, transfer `statusHistory`, `originBillId`, `billIds`, `tableIds`, amounts and lines. An unpaid or multi-bill order can have null `paymentId` and `settlementId`. Build payment records once per bill. Use each bill's quote lines to read allocations when an order spans tables. The order list's status filter selects `accepted`, `preparing` or `completed`. |
| `POST /orders/:id/preparation` | `{ status: "preparing" \| "completed", expectedRevision }`. Moves the order through preparation. |
| `GET /payments/:id/receipt` | Original payment and immutable line snapshots with the current balance, all contributing `orderNos`, and corrections. Each correction contains `lines: [{ allocationId, orderLineId, qty, gross, discount, amount }]` from its recorded effect. `channel` distinguishes `cash_record` and `terminal_record`. Use `terminal` for external references and `transactionNo` for the Navis transaction number. |
| `POST /payments/:id/reversal-quote` | Read-only. `{ kind: "cancel" \| "refund", lines?, amount?, methodAmounts? }`. Returns the existing POS legality and amount breakdown and a quote token bound to that owner, payment state and open day. |
| `POST /settlements/:id/corrections` | `{ quoteToken, confirmed: true, terminal? }`. For a terminal payment, supply the terminal return record. Returns a correction receipt with `paymentId` and `settlementId`. |

Send `Idempotency-Key` on each command and reuse it to recover an uncertain result. Receipts use `{ resourceId, revision, receiptId, affectedSources }` with route-specific fields as listed above. Lists return `{ items, nextCursor, asOf, sourceRevision, sourceFingerprint }`. The numeric revision is a stable page content hash. The full original hash is available in `sourceFingerprint`. `cursor` takes the previous page's `nextCursor`. `limit` defaults to 30 and accepts 1–50. Filter with `status`. Bills and orders accept either `businessDate` or the inclusive pair `from` and `to`, up to 93 days.

For `card` and `easy_pay`, send a `terminal` object with at least one of `approvalNo` and `receiptNo`, plus `occurredAt` as ISO 8601 with an explicit offset. References accept up to 40 ASCII letters, digits, underscores or hyphens and normalize to uppercase. The terminal time must fall within the processing business day and precede or equal the current time. Within each store and business day a reference is unique for sales and separately unique for returns. Cash requests omit `terminal`. POS stores both the terminal time and when the owner recorded it. All reads should display the returned currency and effective time.

Wait for the command receipt and re-read the sources indicated by `affectedSources`. A paid table goes into `cleaning`. Keep the bill and terminal reference visible when a quote changes so the owner can reconcile. Typical responses are `400 VALIDATION` with `TERMINAL_RECORD_REQUIRED` or `CONFIRMATION_REQUIRED`, `404 NOT_FOUND` for a scoped resource, and `409 CONFLICT` with `STALE_REVISION`, `QUOTE_CHANGED`, `DAY_CLOSED`, `TERMINAL_REFERENCE_EXISTS` or `IDEMPOTENCY_MISMATCH`. Payment `QUOTE_CHANGED` supplies the new quote under `details.quote`. For a changed reversal, obtain a fresh quote and confirmation.

## Service integration

- Migration `20261122000200_real_pos_records.sql` adds scoped tables, exclusive sessions, immutable terminal references and revisions on top of the existing POS ledger. The previous app image can run against the expanded schema. The migration's down path protects operating records.
- Migration `20261122000201_real_postpaid.sql` adds layout mapping, session history, editable bill revisions and preparation times. Migration `20261122000202_real_pos_transfer_undo.sql` adds store-scoped transfer receipts. Existing preparations without recorded timestamps return null. A legacy unpaid table draft acquires its original order at its first postpaid edit. The payment path also accepts legacy drafts.
- Order acceptance and transfer state are committed with their command receipts. Recognized sales and inventory movements begin at payment. Splitting apportions each fixed discount in integer won and merging keeps its allocation amounts. The POS service continues to use the catalog at settlement to verify current price, cost and recipe snapshots.
- The existing sale and correction envelopes feed stock, insight and eligible customer projections. Table changes use `pos.table_changed.v1` with table ID, label, seats, state and revision. Table sessions use `pos.table_session_changed.v1` with table ID, bill ID, state and revision. Both share the POS producer sequence. Terminal references stay in the POS receipt record.
- B00 supplies the gateway allowlist, owner route mount, clock and store/business-day provisioning, and carries event contract changes into the shared contract. The migration grants scoped runtime inserts for the verified store ID and day boundary.
- `readCatalog({ storeId, actorId, menuIds })` uses the B01 private `/catalog-snapshot` bulk read with the POS-to-inventory workload credential. Return the snapshot JSON and throw on unsuccessful transport or status. POS looks up the current snapshots once per quote and once at payment commit. An unavailable or malformed source yields `503 CATALOG_UNAVAILABLE`. Missing immutable versions on ordered items or options yield `409 CATALOG_RECIPE_UNAVAILABLE`. Empty recipes can use their real empty-recipe version. The fixture path uses `pos.catalog_menu`.
- F02 supplies the POS HTTP port, checkout UI, same-receipt reload, and authoritative order and table reads. Navis payment and reversal handoffs open the existing POS flow and use masked read facts. B05/B06/B14 supply member, reservation and coupon claim integration. B03/B09/B12 supply operating dependent widgets and finance projections.
